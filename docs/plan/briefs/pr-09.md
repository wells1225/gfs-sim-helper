## Decisions already made

- **On disk.** `<backupsDir>/<backupId>/files/<path inside the Sims folder>` and
  `<backupsDir>/<backupId>/manifest.json` = `{ record: BackupRecord, files: [{ path, bytes, mtimeMs, sha256,
  storedIn }] }`, where `storedIn` is the backup id that holds the bytes. Journal: `<journalDir>/<entryId>.json`.
- **`createBackup(folderPath)`.**
  1. Refuse: game `running` or `unknown`; `backupsDir` inside OneDrive (`paths.oneDriveRoots`, or a path part
     starting `OneDrive`); folder missing; a backup already running; free space (`statfs`) under 1.1 × the bytes to
     copy.
  2. Write the manifest with `state: 'copying'`.
  3. List everything except `CACHE_NAMES` and `BACKUP_ALSO_SKIPS`, `saves` and `Tray` included. Do not follow a link
     that leaves the folder. **Copy only what changed:** a file with the same path, size and whole-millisecond date
     as in the newest `verified` backup is not copied again; its manifest line points at that backup (`storedIn`).
     The rest are copied with `copy` ops (`reason: 'backup'`, `folderPath` set), 200 ops per request at most.
  4. Check every new copy: same size and SHA-256 as its source. All good: `verified`. Any mismatch: `failed`.
  5. Send `copying` and `checking` progress, at most once every 100 ms. Old backups are never removed in v1.
- **`backupStatus`.** Take the newest `verified` backup of that folder. It is `verified` when every file now under
  `Mods` is covered, and `stale` otherwise. A file is covered when the manifest has that path with the same size and
  whole-millisecond date, or when an `applied` journal step put it there (a `move` whose `to` is that path with the
  same size, or an `edit` of that path). No backup: `none`. Any error while checking: `unknown`.
- **A backup comes first, in one place.** `runAction` and `undo` both start by calling `backupStatus`; when it is
  not `verified` they call `createBackup` and pass its progress on. A refused or failed backup returns
  `{ status: 'refused', refusal: { why: 'backup', ... } }` and nothing else happens. Mods that write their own logs
  into `Mods` make "stale" the normal case after she plays, which is why step 3 above copies only what changed.
- **`runAction(plan)`.**
  1. Turn each planned step into a `JournalStep` with `state: 'pending'`. For a `move`, record the size and SHA-256
     now. For an `edit`, record both hashes; `savedCopy` is `<holdingDir>/<entryId>/edits/<file name>`.
  2. Write the journal entry (`in-progress`) **before** the first step.
  3. Run all steps in one gate request (`reason: 'fix'`): `mkdir` for a missing parent, then `move`; for an `edit`,
     `copy` the file to `savedCopy`, then `write` with `replace`; for `remove-cache`, `remove`.
  4. `refused`: remove the journal entry and return the refusal as `{ why: 'gate' }`. `failed`: mark the steps that
     ran `applied`, and check op `opsDone` on the disk (it may have run in part, contract 09abf46); return
     `stopped-part-way`. A cache clear that stops part way says plainly that caches are safe to lose and settles as `done`. `done`: all `applied`, status `done`.
  5. `undo` is `cannot-undo` only when every step is `remove-cache`.
- **`undo(entryId)`.** For each `applied` step, last first: a `move` goes back only when the file at `to` still has
  the recorded hash and nothing sits at `from`; an `edit` is put back only when the file still has `afterSha256`.
  Otherwise skip that step (never overwrite a newer file), put the rest back, set `needs-attention`, and name the
  skipped files by base name in `detail` (Fable's PR 9 check, 2026-11-24). An original back in Mods with an identical spare
  copy in holding is settled by removing the spare copy, only when both match the journal hash and both paths lead to
  their own names. All back: `undone`. A
  second undo of the same entry makes no gate request and returns `done` with the entry.
- **`recover()`.** For each `in-progress` entry, look at the disk to learn which steps ran (the file is at `to` with
  the recorded hash, or still at `from`), then undo those. An entry it cannot settle becomes `needs-attention`. It
  removes only an identical spare copy in holding (as in `undo`) and an entry that surely never ran (every step
  pending, nothing on the disk), which it drops without telling her.
- **One at a time.** Actions, undos and backups run one after another inside the process.

## Tests to write first

Use a small test gate in your own test folder that runs the ops with `fs` under a temp root and counts requests.

- Backup of the `duplicates` fixture: every file except the skipped caches is in the copy with the same hash; the
  manifest says `verified`; `saves` and `Tray` in the source are unchanged.
- A second backup after one file changed copies exactly one file, and a restore list built from its manifest still
  reaches every file. A copy that differs from its source gives `failed`, and `backupStatus` is then `none`.
- Each refusal: game running, game unknown, OneDrive, not enough space (inject `statfs`), already running.
- `backupStatus`: `verified` right after a backup; `stale` after a file appears or changes in `Mods`; still
  `verified` after one of our own actions moved a file.
- `runAction` and `undo` with a stale backup make a backup first; a refused backup stops them with nothing changed.
  `runAction` writes the journal before the first op (the test gate fails if not), and marks steps on a failure.
- **Round trip:** back up `duplicates`, run a move action and an edit action, undo both: the folder is byte for
  byte the original (tree snapshot). Undo twice: the second call makes no gate request.
- Undo refuses when the moved file changed, and when something new sits at `from`. An entry left `in-progress`
  after only some ops ran: `recover()` puts everything back.
